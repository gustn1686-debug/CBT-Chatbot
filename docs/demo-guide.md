# 시연 가이드 (노트북 1대 + RunPod 모델 API)

시연은 **노트북 한 대**에서 백엔드와 프론트를 같이 띄우고, 모델은 모델팀이 RunPod 서버리스에 올려 둔 API(`model/README.md`)를 호출한다. 배포(AWS/Vercel/Supabase)는 필요 없다.

```
[노트북]
  브라우저 ── 프론트(5173) ── 백엔드(8000, SQLite) ──(인터넷)──▶ [RunPod 서버리스] 상담 모델
                                  1) POST /run  → 작업 ID
                                  2) GET /status/{ID} 를 반복 조회 → output.reply
```

모델 API는 **작업을 제출하고 결과를 조회하는 방식**이라 답변이 완성된 뒤 한꺼번에 온다. 백엔드가 그 답변을 조각으로 나눠 화면에 흘려 보내므로, 사용자에게는 한 글자씩 나오는 것처럼 보인다. 응답이 오기 전에는 "• • •"가 보인다.

## 0. 역할

| 누가 | 할 일 |
|---|---|
| 모델팀 | RunPod 엔드포인트를 시연 시간에 쓸 수 있게 켜 두고, **호출용 키**를 별도로 전달 |
| 백엔드/프론트 | 아래 순서로 노트북에서 실행 |

모델팀에 확인할 것
- **서버를 미리 켜 둘 수 있는지**: 서버리스는 사용이 없으면 꺼져 있다가 첫 요청에 켜지므로, 27B급 모델이면 **첫 응답이 몇 분** 걸릴 수 있다. 시연 시간에는 최소 워커 1개를 켜 두거나, 시연 직전에 한 번 깨워 두어야 한다.
- **`messages`에 `system` 메시지를 넣어도 되는지**: 되면 `RUNPOD_SEND_SYSTEM_PROMPT=true`로 우리 시스템 프롬프트와 이전 대화 요약을 같이 보낸다. (기본은 끔)
- **요약 요청이 되는지**: 이 API가 상담 응답 전용이면 회기 요약을 만들 수 없다. 가능하면 `RUNPOD_SUMMARY_ENABLED=true`. (기본은 끔)
- 동시에 몇 명까지 처리되는지 (시연 인원 5~10명)
- 시연 시간대에 그 GPU/엔드포인트를 학습·평가에 같이 쓰지 않기

## 1. 처음 한 번만 (준비)

필요한 것: Python 3, Node.js, 이 저장소 클론, **모델팀에게 받은 호출용 키**.

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
```

```bash
cd frontend
npm install
```

### 환경변수 — 파일이 둘로 나뉜다

백엔드와 프론트는 **서로 다른 `.env` 파일**을 읽는다. (둘 다 git에 올라가지 않는다)

**① 레포 루트 `.env`** — 백엔드가 읽는다. `.env.example`을 복사해서 만든다.

```bash
cp .env.example .env
```

```
JWT_SECRET=<아무 긴 문자열로 변경>
CRISIS_LOG_SECRET=<아무 긴 문자열로 변경>

LLM_MODE=runpod
RUNPOD_ENDPOINT_URL=https://api.runpod.ai/v2/<엔드포인트 ID>   # model/README.md 의 API 주소
RUNPOD_API_KEY=<모델팀에게 받은 키>
```

> **키는 이 `.env`에만 넣는다.** 저장소, 채팅, 이슈, 스크린샷에 붙여넣지 않는다. `.env`는 `.gitignore`에 들어 있어 커밋되지 않는다.

**② `frontend/.env.local`** — 프론트(Vite)가 읽는다. 루트 `.env`의 `VITE_*` 값은 프론트에 **적용되지 않는다**.

```
VITE_USE_MOCK=false
VITE_API_BASE_URL=http://localhost:8000/api/v1
```

`VITE_USE_MOCK=false`를 빼먹으면 화면은 뜨지만 가짜(목업) 응답이 나온다.

### DB 만들기

```bash
cd backend
source .venv/bin/activate
alembic upgrade head
```

로컬 SQLite 파일(`backend/synap.db`)이 만들어진다.

## 2. 모델 API부터 확인 (우리 코드와 무관하게)

백엔드를 띄우기 전에, 모델 API 자체가 되는지 먼저 본다.

### 연결 점검 스크립트 (권장)

루트 `.env`에 `LLM_MODE=runpod`, `RUNPOD_ENDPOINT_URL`, `RUNPOD_API_KEY`를 넣은 뒤 실행한다. 설정 확인, 작업 제출, 결과 조회, 응답 시간까지 한 번에 점검하고 안 되면 원인과 해결 방법을 알려 준다. **키 값은 출력하지 않는다.**

```bash
cd backend
source .venv/bin/activate
python -m scripts.check_model_api          # 기본 점검 (제출 → 조회 → 답변)
python -m scripts.check_model_api --all    # 2번째 턴, system 메시지, 작업 취소까지 모두 점검
```

- 점검이 모두 통과하면 종료 코드 0, 하나라도 실패하면 1이다.
- 첫 요청은 서버가 꺼져 있었다면 오래 걸린다. 기본으로 최대 300초(`--timeout`)까지 기다리며 상태가 바뀌는 시간을 보여 준다. **이 시간이 시연 때 첫 응답 시간이다.**
- 응답 시간이 `RUNPOD_JOB_TIMEOUT`(기본 120초)에 가까우면 주의 표시가 뜬다.
- `--all`의 선택 점검은 모델에 요청을 더 보내므로 GPU 시간을 조금 더 쓴다.
  - **system 메시지**: 거절 없이 처리되는지만 본다. 지시가 실제로 반영되는지는 모델팀에 확인해야 한다. (`RUNPOD_SEND_SYSTEM_PROMPT`를 켜도 되는지 판단하는 참고용)
  - **작업 취소**: `POST /cancel/{id}`가 되는지 본다. 안 돼도 백엔드는 동작하지만, 시간 초과된 작업이 서버에 남을 수 있다.

### 직접 `curl`로 확인 (`model/README.md`와 같은 방법)

```bash
API=https://api.runpod.ai/v2/<엔드포인트 ID>
export RUNPOD_API_KEY=<키>
curl -sS -X POST "$API/run" \
  -H "Authorization: Bearer $RUNPOD_API_KEY" -H "Content-Type: application/json" \
  -d '{"input":{"messages":[{"role":"user","content":"내일 발표가 걱정돼요."}]}}'
```

`{"id":"...","status":"IN_QUEUE"}`처럼 작업 ID가 오면 제출은 된 것이다. 받은 ID로 결과를 본다.

```bash
curl -sS "$API/status/<작업 ID>" -H "Authorization: Bearer $RUNPOD_API_KEY"
```

`IN_QUEUE`/`IN_PROGRESS`면 잠시 뒤 다시 조회하고, `COMPLETED`가 되면 `output.reply`에 답변이 있다. **이 첫 요청이 얼마나 걸리는지 꼭 확인한다.** (서버가 꺼져 있었다면 오래 걸린다. 이게 시연 때 첫 응답 시간이다)

## 3. 실행 (터미널 두 개)

```bash
cd backend
source .venv/bin/activate

```

```bash
cd frontend
npm run dev
```

브라우저에서 **`http://localhost:5173`** 을 연다.

> 주소는 꼭 `localhost:5173`이어야 한다. `127.0.0.1`이나 `npm run preview`(4173 포트)로 열면 백엔드 CORS(`CORS_ORIGINS`, 기본 `http://localhost:5173`)에 막힌다.

## 4. 시연 전 리허설 체크리스트

- [ ] 2번의 `curl`로 모델 API가 응답한다 (키가 맞고, 서버가 켜져 있다)
- [ ] **시연 직전에 한 번 깨워 둔다** (아무 메시지나 한 번 보내 서버리스를 켠다)
- [ ] 대화에서 응답이 오고, 한국어 상담 톤이 나온다
- [ ] 첫 응답까지 걸리는 시간이 허용 범위다 (`RUNPOD_JOB_TIMEOUT` 안에 들어온다)
- [ ] 두 번째 턴에서 앞선 대화를 이어서 대답한다 (이력이 함께 전달된다)
- [ ] 위기 표현(`죽고 싶어요`)에서 전화 안내 시트가 뜬다 (모델을 호출하지 않고 서버 고정 문구)
- [ ] 노트북이 인터넷에 안정적으로 연결돼 있다 (화면 잠금·절전 해제)
- [ ] 백업 준비: 녹화 영상 또는 `LLM_MODE=mock` 전환 방법 확인

회기 요약은 `RUNPOD_SUMMARY_ENABLED=true`로 켰을 때만 만들어진다. 켠 경우 다른 대화로 옮기거나 "새 대화"를 누른 뒤 요약이 저장되는지 확인한다.

```bash
cd backend
sqlite3 synap.db "select title, summary_seq, summary from conversations"
```

`summary`에 JSON(상황, 처음 떠오른 생각, 감정 등)이 들어 있어야 한다. 요약 프롬프트는 mock에서만 확인했고 **실제 모델로는 검증하지 않았다.**

### 상담 계획 · 알림 · 요약 (회원만)

**알림 키 (처음 한 번)**: 상담 시간 알림(웹 푸시)을 보내려면 서버 키가 필요하다. 없으면 알림만 꺼지고 나머지는 동작한다.

```bash
cd backend
source .venv/bin/activate
pip install -r requirements.txt      # pywebpush 가 새로 들어왔다
python scripts/generate_vapid_keys.py
```

출력된 `VAPID_PUBLIC_KEY=…`, `VAPID_PRIVATE_KEY=…` 두 줄을 **루트 `.env`** 에 붙여 넣고 백엔드를 다시 켠다. 개인키는 비밀이다 (저장소·채팅에 올리지 않는다). DB도 한 번 올린다: `alembic upgrade head`

**리허설 체크**

- [ ] 회원으로 로그인 → 메뉴(☰) → "상담 계획" → "상담 계획 세우기" → 횟수·요일·시각 고르고 "계획 시작하기" → 브라우저가 알림 권한을 물으면 허용
- [ ] 상담 계획 화면의 "테스트 알림 보내기" → 알림이 뜨고, 누르면 앱이 열린다
- [ ] 대화를 나누고 입력칸 위 "상담 마치기" → 도장이 찍히고 "오늘 나눈 이야기" 요약이 나온다 (모델 요약이라 몇 초~수십 초)
- [ ] 마지막 회기까지 마치면 상담 계획 화면에 "전체 회기 요약"이 나온다
- [ ] 실제 예약 알림: 일정을 지금부터 2~3분 뒤로 바꾸고 기다린다 (서버가 30초마다 확인한다)

알림이 오는 환경: 노트북 Chrome·Edge는 `http://localhost:5173`에서도 된다. **아이폰은 Safari에서 "홈 화면에 추가"로 설치한 앱에서만** 받는다 (iOS 16.4+, https 주소 필요 — 배포 후). 브라우저나 OS의 알림 설정(집중 모드·방해 금지)이 꺼져 있으면 오지 않는다.

시연 시간을 줄이려면 계획 횟수를 **3회**로 만든다.

## 5. 시연 흐름 예시

화면은 ChatGPT 앱과 같은 구조다. 앱을 열면 바로 새 대화 화면이고, 왼쪽 위 메뉴(☰)에 지난 대화 목록이 있다. 오른쪽 위에는 비회원이면 "로그인"이 있고, 회원은 비어 있다 (설정·상담 계획은 왼쪽 메뉴에). (별도의 홈 화면, 하단 탭바, "대화 종료" 버튼은 없다)

1. 시작 화면에서 "비회원으로 먼저 써볼게요" → 바로 새 대화 화면
2. 고민을 이야기하고 응답 확인
3. 왼쪽 위 메뉴(☰) → "지난 대화"에 방금 대화가 보임. 다른 대화로 옮기거나 "새 대화"를 누르면 이 대화는 서버가 요약해 둔다. **비회원은 이때 "대화를 보관하려면 가입이 필요해요. 가입하시겠어요?"가 먼저 뜬다** ("가입하기" → 가입 화면, "나중에 할게요" → 그대로 이동)
4. 목록에서 지난 대화를 눌러 이어서 대화
5. (선택) 가입 → 로그아웃 후 로그인, 대화가 이어지는지 확인
6. (선택) 위기 표현 → 상담 전화 안내 시트
7. (회원) 메뉴 → 상담 계획 → 3회·매일·밤 10시로 계획 → 알림 허용 → "테스트 알림 보내기"
8. (회원) 새 대화에서 "오늘은 1회기 상담이에요" 확인 → 이야기 → "상담 마치기" → 도장 + 회기 요약
9. (회원, 미리 준비) 3회기를 모두 마친 계정으로 상담 계획 화면 → 전체 회기 요약

> 모델이 이전 대화 요약을 기억하는 기능(새 대화가 지난 대화를 기억)은 **`RUNPOD_SEND_SYSTEM_PROMPT`와 `RUNPOD_SUMMARY_ENABLED`가 켜져 있을 때만** 동작한다. 모델 API가 이를 받지 못하면 시연에서는 "지난 대화 목록과 이어서 대화하기"까지만 보여준다.

> 위기 감지의 키워드·문구·전화번호는 **임시안**이다. 위기 표현은 LLM을 부르지 않고 서버의 고정 문구로 응답한다.

## 6. 문제가 생기면

| 증상 | 원인과 해결 |
|---|---|
| 첫 메시지가 한참 걸리다 "응답이 늦어지고 있어요 · 다시 시도"가 뜸 | 서버리스가 꺼져 있다 켜지는 중(콜드 스타트). 한 번 더 시도하거나, `RUNPOD_JOB_TIMEOUT`(기본 120초)을 늘리고 모델팀에 서버를 켜 둬 달라고 요청 |
| 보낸 메시지에 "전송 실패"가 뜨고 응답이 없음 | 모델 API 연결 실패(`llm_unavailable`). 백엔드 로그에서 원인 확인: 키(`RUNPOD_API_KEY`)·주소(`RUNPOD_ENDPOINT_URL`) 오류, 작업 `FAILED`/`CANCELLED`/`TIMED_OUT`. 2번 `curl`로 확인 |
| 백엔드 로그에 "RUNPOD_ENDPOINT_URL 또는 RUNPOD_API_KEY 가 설정되지 않았습니다" | 루트 `.env`에 값이 없거나, `.env` 수정 후 백엔드를 재시작하지 않음 |
| "모델 서버 인증에 실패했습니다" | 키가 틀리거나 만료됨. 모델팀에 키 확인 |
| "지금 이용하는 분이 많아요" | 우리 쪽 동시 호출 제한(8번)이거나 RunPod의 요청 제한(429). 잠시 후 다시 시도 |
| 가짜 같은 짧은 응답만 나옴 | `LLM_MODE`가 `mock`이거나 백엔드를 재시작하지 않음 |
| 화면은 뜨는데 응답이 항상 정해진 문장(목업) | `frontend/.env.local`의 `VITE_USE_MOCK=false` 누락. 프론트 재시작 |
| 브라우저 콘솔에 CORS 오류 | 주소를 `http://localhost:5173`으로 열었는지 확인 |
| 로그인/대화 API가 500 | `alembic upgrade head`를 했는지 확인. 예전 `synap.db`가 있으면 지우고 다시 `alembic upgrade head` |

모델 API가 끝내 안 되면 `.env`에서 `LLM_MODE=mock`으로 바꾸고 백엔드를 재시작하면 화면 흐름만이라도 보여줄 수 있다.

## 7. 리허설 후 초기화 / 끝난 뒤

대화 기록을 비우고 처음부터 다시 하려면:

```bash
cd backend
rm synap.db
alembic upgrade head
```

그리고 브라우저에서 사이트 데이터(localStorage)를 지우거나 시크릿 창을 쓴다. (로그인 토큰이 남아 있으면 지워진 계정으로 접속을 시도해 401이 난다.)

시연이 끝나면 모델팀에 엔드포인트를 줄여 달라고(최소 워커 0) 알려 비용을 아낀다.

## 8. 모델 호출 보호 (동시 호출 제한 · 타임아웃)

백엔드가 모델 API를 보호한다. 기본값은 시연(5~10명)에 맞춰 두었고, 루트 `.env`로 바꿀 수 있다. (`.env.example` 참고)

| 상황 | 동작 | 사용자에게 |
|---|---|---|
| 동시에 응답을 생성하는 요청이 `LLM_MAX_CONCURRENT`(기본 8)개를 넘음 | 최대 `LLM_QUEUE_WAIT_SECONDS`(20초) 기다리게 함 | 평소처럼 응답 |
| 기다리는 줄이 `LLM_MAX_QUEUE`(8)를 넘거나 20초를 기다려도 자리가 안 남 | 바로 거절 (`llm_busy`) | "지금 이용하는 분이 많아요 · 잠시 후 다시 시도" |
| RunPod가 요청 제한(HTTP 429)으로 거절 | `llm_busy`와 같이 처리 | 위와 같음 |
| 작업이 `RUNPOD_JOB_TIMEOUT`(120초) 안에 끝나지 않음 | 중단하고 **RunPod 작업도 취소**(`/cancel/{id}`, 실패해도 무시) (`llm_timeout`) | "응답이 늦어지고 있어요 · 다시 시도" |
| 작업이 `FAILED`/`CANCELLED`/`TIMED_OUT`, 결과 조회가 연달아 3번 실패, 답변이 비어 있음 | 오류 (`llm_unavailable`) | "전송 실패 · 다시 시도" |
| 사용자가 화면을 닫음 | 기다리던 RunPod 작업을 취소하고 자리를 반납 | - |
| 회기 요약 | 대화 응답과 **별도로** `LLM_SUMMARY_MAX_CONCURRENT`(1)개씩만 | 보이지 않음 |

- 결과 조회가 일시적으로 한두 번 실패하는 것은 넘어간다. 연달아 3번 실패하면 포기한다.
- 응답이 실패한 턴 뒤에 같은 말을 다시 보내거나 다른 말을 이어 보내도, 모델에는 `user`/`assistant`가 번갈아 오도록 정리해서 보낸다.
- A100 급 서버에서 적정한 동시 수는 리허설에서 정한다.

## 9. 알려진 한계 (시연 전에 알아둘 것)

- 서버리스의 **콜드 스타트 시간은 우리가 줄일 수 없다.** 시연 전에 서버를 깨워 두는 것이 가장 중요하다.
- 답변이 완성된 뒤에 화면에 나타나므로, 긴 답변도 "• • •"가 보이다가 한꺼번에 흘러나온다. (진짜 스트리밍이 아니다)
- 모델 API가 system 메시지와 요약 호출을 받는지 확인되기 전까지 "이전 대화 기억" 기능은 꺼져 있다.
- 동시 호출 제한 값은 **어림값**이다. 실제 서버로 부하 테스트를 해 보고 맞춰야 한다.
- 위기 문구와 키워드는 임시안이다. (전문가 검토 필요)
- 비밀번호 재설정, 이메일 인증은 없다.
- 상담 시간 알림은 **백엔드가 켜져 있을 때만** 보낸다 (서버 안에서 30초마다 확인). 서버를 껐다 켜는 사이의 예약은 15분 안이면 보내고, 넘으면 건너뛴다.
- 회기·전체 요약의 모델 모드는 모델팀이 합성 데이터로 확인했다 (`model/README.md`, 5회기 기준). 우리 서버에서 실제 모델로 요약까지 이어서 돌려 본 것은 리허설에서 확인해야 한다.
